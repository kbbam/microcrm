# microcrm engineering contract

This repository is a production CRM, not a disposable prototype. Work from evidence: reproduce a failure, identify its cause, make the smallest coherent change, and verify the user-visible behavior. Do not stack speculative fixes.

Read `README.md`, `server/README.md`, and `docs/ENGINEERING_ASSESSMENT.md` before changing behavior. Treat the code and current runtime evidence as authoritative when documentation disagrees with them, and update stale documentation in the same change.

## Architecture and ownership

- `template.html` and `data.json` are the editable sources for the static CRM.
- `index.html` and `artifact.html` are generated by `python3 build.py`. Never edit either generated file directly. When a source changes, regenerate and include both outputs.
- `server/src/` is the editable TypeScript API source. `server/dist/` is generated by `npm run build`; never patch it directly.
- Postgres is the source of truth for edits made through the live MCP connector. `data.json` is a snapshot, not a live database mirror.
- The browser app can fall back from live MCP data to its embedded snapshot. A page that renders is not proof that live synchronization works; verify the live indicator and network/tool behavior explicitly.

## Required workflow

1. Inspect `git status` and preserve all pre-existing work. Never discard, overwrite, or silently fold unrelated changes into the task.
2. Reproduce the reported behavior before editing. Record the exact command, request, or browser path and the observed result.
3. For non-trivial bugs, delegate initial diagnosis to `bug-investigator`. Keep it read-only.
4. Delegate a scoped, evidence-backed change to `implementation-engineer`. Do not run multiple writing agents against the same files concurrently.
5. After implementation, delegate independent verification to `qa-release-gate`. A fix is incomplete if the gate finds a regression or if the original symptom was not retested.
6. Report changed files, commands actually run, their results, and any checks that could not be run. Never claim a test passed without command output from the current revision.

## Verification floor

Run the checks relevant to every changed area.

Static app or dataset:

```bash
python3 -m json.tool data.json >/dev/null
python3 -m py_compile build.py research/*.py
python3 build.py
```

After the build, confirm `index.html` and `artifact.html` are the only generated outputs and match the intended `template.html`/`data.json` change. For UI behavior, test both snapshot mode and live mode; test a list/search path and a detail path.

Server:

```bash
cd server
npm ci
npm run build
```

The server integration suite requires an isolated Postgres database:

```bash
cd server
DATABASE_URL=postgresql://postgres:test@localhost:5432/microcrm_test \
  LOCAL_INSECURE_DB=1 npm test
```

CI runs static generation checks and the server integration suite on every PR
and push to `main`. Bug fixes should add a regression test whenever practical;
compilation alone is not behavioral verification.

Production-safe read-only smoke checks:

```bash
curl -fsS https://microcrm-api-production.up.railway.app/healthz
curl -fsS https://microcrm-api-production.up.railway.app/readyz
curl -fsS https://microcrm-api-production.up.railway.app/version
curl -i https://microcrm-api-production.up.railway.app/mcp
curl -fsS https://microcrm-api-production.up.railway.app/.well-known/oauth-protected-resource/mcp
curl -fsS https://microcrm-api-production.up.railway.app/.well-known/openid-configuration
railway status
```

Expected: `/healthz` returns 200 JSON; unauthenticated `/mcp` returns 401 with `WWW-Authenticate`; both discovery documents return 200 and advertise the production issuer/resource. Do not use credentials in routine smoke checks.

## Safety boundaries

- Never run `npm run migrate` against a production or tunneled database without explicit user approval, a current backup, and a reviewed reconciliation plan. The migration replaces each existing entity/person JSON document with the repository snapshot and can erase live CRM edits.
- Never expose or commit `DATABASE_URL`, `ADMIN_TOKEN`, `COOKIE_SECRET`, OAuth tokens, invite tokens, passwords, or JWKS private material. Redact them from logs and reports.
- Never commit, push, deploy, create invites, mutate production data, or restart services unless the user explicitly asks for that action.
- Do not validate OAuth by weakening PKCE, token checks, TLS, cookies, or resource-indicator validation.
- Do not use `LOCAL_INSECURE_DB=1` except with a genuinely local non-TLS Postgres instance.
- Treat contacts arrays as replacement writes. Fetch the current record first and preserve existing contacts when adding one.

## Definition of done

A task is done only when the original failure is reproduced and then no longer reproduces, a regression check exists or the missing harness is called out explicitly, generated files are synchronized, relevant builds pass, documentation matches behavior, and `git diff` contains only intended changes.
